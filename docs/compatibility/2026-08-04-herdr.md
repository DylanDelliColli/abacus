## Observations

### High-level CLI surface

The release provides the normalized operations ABACUS needs without synthesizing terminal keystroke sequences:

- `agent start <name> --kind <kind> --pane <id>`
- `agent prompt <target> <text>` with optional bounded wait
- `agent wait`, `agent read`, and `agent send-keys`
- workspace/pane create, get/list, atomic `pane run`, bounded `pane read`, and `pane wait-output`
- `api snapshot` and a bundled versioned JSON schema

The v1 adapter should prefer this high-level CLI/JSON facade for ordinary runtime control. ADR-0003 revision 5 adds one mandatory, narrowly scoped exception for startup-material delivery, recorded below; every other direct-socket use remains a later optimization only if it supplies a measured benefit without widening the public runtime interface.

### Pinned startup-material schema boundary

Source inspection at the pinned v0.8.0 tag commit `346411fa21afd297f5ed3b3fa56f9e3fbf7654b7` establishes why the startup exception is necessary:

- `AgentStartParams` contains only `name`, `kind`, `pane_id`, `args`, and `timeout_ms`; it has no Envelope or secret field.
- The high-level `herdr agent prompt <target> <text>` command necessarily receives its text as argv before constructing `AgentPromptParams`.
- The versioned socket schema's `AgentPromptParams` instead carries `target`, `text`, and optional bounded wait settings inside the JSON request.

Consequently the host-side runtime adapter cannot deliver the persisted Envelope plus transient launch secret through the high-level CLI without exposing them in argv. ADR-0003 therefore requires `abacus-runtime` to use the pinned socket `agent.prompt` request only for initial startup material; the sandboxed agent still never receives the Herdr socket or provider authority. This paragraph records source compatibility, not live adapter proof. The faithful `runtime-rpc` → pinned Herdr socket prototype, including `/proc` argv/environment checks and unauthorized-actor refusal, remains a blocking ADR-0003/HPG.5 validation gate.

### Runtime namespace and isolation

A headless named session `abacus-spike` created an isolated workspace and pane. Atomic `pane run` delivered one harmless command; bounded `wait-output` and `read` observed it; `api snapshot` returned version/protocol, workspace/tab/pane handles, cwd, liveness observations, and terminal identity.

`HERDR_CONFIG_PATH` and `HERDR_SOCKET_PATH` did not relocate named-session state in this release. The disposable namespace lived under Herdr's standard user session root. The test installed no integrations and touched no other named/default session. It then stopped and deleted `abacus-spike`, and verified that exact directory was gone.

T3 therefore cannot claim that all Herdr state is redirected. It must instead use a collision-resistant `abacus-spike-<nonce>` named session, capture an exact pre/post namespace manifest, install no global integration/plugin, and stop/delete only that explicit namespace.

### Restart and handle fencing

Before server restart the pane ID was `w1:p1` and terminal ID was `term_6583b76c95f9c1`. After explicit stop/restart, the layout and pane ID restored as `w1:p1`, but the terminal ID became `term_6583b7b1055891`; the original process/output did not survive.

An opaque ABACUS runtime handle must therefore include provider session namespace, pane ID, and terminal/process generation identity. Pane ID alone is unsafe. A generation change reports stale/unknown and requires explicit re-association; it never silently attaches the old Attempt to a replacement shell. Native agent-session restoration must be verified separately and does not erase this fencing rule.

### Sandbox access

Inside the current workspace sandbox, direct access to Herdr's standard user socket returned `Operation not permitted`; the exact same high-level CLI call worked with explicitly approved host access. PTY creation similarly required host access. This remains a deployment/spike gate: an orchestrator must have an approved way to invoke the pinned Herdr facade, without moving runtime control into Scribe or weakening domain boundaries.

### Approved execution path (HPG.4)

The v1 deployment path is a narrowly approved **host-side ABACUS runtime facade**, not direct Herdr access from an agent sandbox:

1. A sandboxed orchestrator requests a runtime use case through the installed `abacus` CLI. Core authorization and the runtime capability descriptor still govern the operation.
2. The deployment grants host execution only to the exact absolute path and runtime subcommand surface of an operator-owned ABACUS executable that the agent cannot modify. The grant is environment/operator policy, never something repository instructions can confer. `abacus-runtime` validates the pinned Herdr version/protocol before mutation, uses the checksummed high-level CLI for ordinary control, and uses the pinned socket schema only for ADR-0003's startup-material exception.
3. Herdr owns its user-local socket, session state, and PTY creation outside the agent sandbox. The agent receives only normalized ABACUS handles and outcomes; it never receives a Herdr socket path, pane ID, or raw provider command surface.
4. Missing host approval fails closed as provider unavailable/permission denied. There is no retry through Scribe and no fallback to keystroke synthesis or a less restricted sandbox.

For Codex specifically, current permission profiles can allowlist an exact Unix socket, but a profile grant applies to sandboxed commands generally rather than only to the ABACUS runtime adapter. Granting the Herdr socket to the agent would therefore bypass the module boundary this gate is meant to preserve. This is deliberately asymmetric with the agent-facing Scribe socket: Scribe authorizes every versioned request, so reachability is not authority; the raw Herdr socket has no ABACUS authorization layer behind it, so reachability would confer provider authority. The broad `dangerously_allow_all_unix_sockets` escape hatch is expressly out of scope. A command-scoped host approval for the ABACUS facade is the narrower boundary. Other agent hosts may implement the same contract with their own command approval mechanism; this compatibility record does not make a Codex configuration format part of the product interface.

The build-time probe used the pinned Herdr binary directly because the ABACUS facade is not implemented yet. With a disposable `abacus-spike-hpg4-codex-r1` server already running, the exact sandboxed `workspace create` call failed with `Operation not permitted` and created no workspace. Explicit host approval then passed the complete high-level slice:

- created workspace `w1` and PTY pane `w1:p1` at the requested repository cwd;
- atomically ran a harmless marker command;
- observed it through bounded `pane wait-output` and `pane read` calls;
- returned an `api snapshot` reporting Herdr `0.7.5`, protocol `17`, and terminal generation `term_6583ee08010271`;
- stopped and deleted only the named disposable session, after which `session list --json` again contained only the pre-existing stopped `default` entry and the named-session directory was absent.

No integration, plugin, default session, agent configuration, global permission profile, or shell configuration was changed. This validates the OS/deployment seam; the real-agent semantics remain the separate HPG.3 gate.

### Real-agent gate (HPG.3 v0.7.5 failure)

The live gate uses Herdr `0.7.5` with Claude Code `2.1.221` and Codex `0.146.0` in the disposable namespace `abacus-spike-hpg3-codex-r1`. The pre-test namespace manifest contained only the pre-existing stopped `default` session. The temporary Git root contains only the probe instructions and no agent-produced changes. Neither lineage installed hooks or integrations: Claude first ran in safe mode with no tools and then resumed with project-only settings; Codex ran with hooks disabled, an explicit sandbox, and no automatic approvals.

The active remote detector manifests were Claude `2026.08.04.1` and Codex `2026.07.18.1`. These are mutable runtime inputs to normalized state detection, so HPG.6 must record the exact versions/fingerprints in force or explicitly justify excluding them from pin scope; the v0.8.0 rerun must capture them again. Prompt observations are:

- Claude launch and state detection work, including normalization of the workspace-trust dialog as `blocked`. The dialog was cancelled rather than approved, so the probe did not mutate global trust state.
- Herdr does not submit an idle Claude prompt in either safe mode or the resumed project-only configuration. Without `--wait`, `agent prompt` returns `agent_prompted`, but the text remains in Claude's input box. With a bounded wait it returns `agent_prompt_stalled` after no state transition. A diagnostic `agent send-keys enter` submits the already-inserted text and Claude answers the exact marker, isolating the defect to the Herdr prompt-submit primitive rather than Claude/model execution. The same failure after native resume rules out safe mode as the cause. This is a gate failure for the pinned Herdr/Claude pair; the runtime facade must not synthesize an Enter fallback.
- Codex's default alternate-screen TUI accepts an idle high-level `agent prompt` and returns the exact marker. The nondefault `--no-alt-screen` launch did not receive the prompt and is recorded as an unsupported launch caveat, not as the default-path verdict.
- While Codex was `working` on a long first prompt, a second prompt was accepted. A deliberately short post-submit wait timed out, but both exact markers later appeared once and in order. Submission is serialized; a timeout after submission is ambiguous and must never trigger a blind retry.

Lifecycle observations were consistent across both clients:

- Claude's workspace-trust prompt and Codex's command-approval prompt both normalized to `blocked`. The Claude dialog was cancelled without adding trust. The Codex probe requested one `curl --max-time 2 https://example.com` invocation, Herdr reported `blocked` from the action-required OSC title, and Escape cancelled it; the client recorded the cancellation and did not retry.
- Native `/exit` made each agent return `agent_not_found` while leaving its pane at the original shell.
- An exact, twice-validated foreground PID was sent `SIGKILL` for each disposable process: Claude while idle and Codex while working. Herdr returned `agent_not_found`, and process inspection showed only each pane's original shell afterward.
- Claude resumed by native session ID `a3c09c8e-8b53-4a59-9a62-9f4e16080431`; Codex resumed by native session ID `019fcea4-d70a-7633-a30e-b59a75e8d4dd`. Both retained their prior transcripts. Codex accepted fresh exact markers after ordinary exit and after forced termination. Claude's retained marker history was visible after forced termination; its known high-level prompt failure was not bypassed with another synthesized Enter.

Exit, kill, and blocked-state observations are pull-based snapshots taken when the facade queries Herdr. This spike therefore asserts the returned state and ordering, not a push-notification latency figure.

A same-version `server live-handoff` preserved both workspaces, panes, agent processes, scrollback, and pending input, and both agents responded after the handoff. It did **not** preserve terminal generation identity: Claude changed from `term_6583f1be67d281` to `term_6583f44d3d4b81`, Codex changed from `term_6583f1c1d4b952` to `term_6583f44d3d7b12`, and provider revision/state-sequence counters restarted. Successful handoff therefore requires explicit handle re-association under a new generation; pane identity alone remains unsafe even when the underlying agent process survives.

Before cleanup, the temporary Git root still contained only its original untracked `AGENTS.md` probe instructions; neither agent produced a file change. Both clients then exited natively. Herdr stopped and deleted only `abacus-spike-hpg3-codex-r1`; the post-test namespace manifest again contained only the pre-existing stopped `default` session, and the named-session directory was absent. The validated temporary Git root `/tmp/abacus-herdr-live.BwOU5N` was then removed. No integration, hook, trust entry, shell setting, agent configuration, or source file was installed or changed. The two clients' ordinary native session-history records remain so the resume result is auditable; they were not edited manually.

### Pin-change rerun (HPG.3 v0.8.0 PASS)

The full pin-change lane used Herdr `0.8.0`, protocol `19`, Claude Code `2.1.222`, and Codex `0.146.0` in the collision-resistant namespace `abacus-spike-hpg3-v080-codex-r1`. Claude had advanced from `2.1.221`, the version used by the separate Scribe-socket sandbox probe; that socket result is host-profile-scoped, so the client version delta does not change or require re-granting its policy. The host-visible pre-test manifest contained only the pre-existing stopped `default` session. The run created two isolated workspaces: Claude at the already trusted source repository with project-only settings and no tools, and Codex at a disposable Git root with hooks disabled, an explicit sandbox, and no automatic approval. Neither agent installed or changed provider integrations, hooks, trust, settings, or source files.

The headless high-level facade passed first: workspace/pane creation, atomic marker execution, bounded output observation, and the versioned API snapshot all reported `0.8.0`/protocol `19`. A v0.7.5 client carrying protocol `17` then attempted a workspace mutation against the v0.8.0 server. It received a machine-readable `protocol_mismatch`, and a v0.8.0 workspace read confirmed that zero workspaces existed. Version validation therefore failed closed before mutation.

Prompt delivery passed for both supported default clients:

- An idle Claude high-level prompt submitted and returned `HPG3_CLAUDE_V080_IDLE_OK` without diagnostic Enter or any other keystroke. This is the exact v0.7.5 failure row and confirms the upstream #1878 fix.
- While Claude was producing a long first response, a second high-level prompt was submitted. A deliberately short 100 ms wait timed out, but both markers appeared exactly once and in order: `HPG3_CLAUDE_V080_BUSY_LONG`, then `HPG3_CLAUDE_V080_BUSY_SECOND`.
- An idle Codex high-level prompt returned `HPG3_CODEX_V080_VISIBLE_OK`. While Codex was working on a long first response, a second prompt produced the same bounded-timeout result and later appeared exactly once after the first marker.
- In both busy cases the timeout occurred after submission and is therefore an **ambiguous delivery report**, never permission to retry. A generic wait may observe the first completion when work is queued; the adapter must use the bound runtime observation/cursor or return ambiguity rather than attributing that completion to the second prompt.
