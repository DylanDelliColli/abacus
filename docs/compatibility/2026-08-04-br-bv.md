## Observations

### Prefix mapping

`br init --prefix ABACUS` succeeds but normalizes generated IDs to lowercase (`abacus-...`). Setting `issue_prefix=ABACUS` later preserves the displayed config value while the computed prefix and newly generated IDs remain lowercase. Lookups are case-insensitive: `br show ABACUS-aon --json` resolves the stored `abacus-aon` record.

ABACUS therefore needs an explicit lossless seam mapping:

```text
ABACUS external ID: ABACUS-<lowercase suffix>
br provider ID:     abacus-<lowercase suffix>
```

Lowercase provider IDs and provider-generated command strings never cross the work facade. Fresh ABACUS initialization rejects conflicting/mixed graphs rather than guessing a mapping. This preserves the binding `ABACUS-` product namespace without forking `br` solely for case presentation.

### Machine operations and graph semantics

The spike exercised JSON output for initialize, create, show, ready, update, dependency-add, close, list, info, and sync-status. Dependency direction matched the required contract: `br dep add child blocker` removed the child from `ready`; closing the blocker made the child ready.

`br close ... --reason accepted_handoff --json` persisted and returned the curated close reason. The adapter can therefore render the bounded ABACUS reason code directly and must reject arbitrary/unbounded message content before invoking the provider.

Mutations auto-flushed `issues.jsonl`. `br sync --status --json` returned `dirty_count: 0` and a 64-hex `jsonl_content_hash`, suitable as the provider revision observed before and after composed reads.

### Concurrency

Two simultaneous atomic claims against one open bead produced exactly one success. The loser returned exit code `4` with structured code `VALIDATION_FAILED`, a field/reason context, and `retryable: true`; the database remained readable. ABACUS still serializes decision-gated mutations at its use-case boundary and normalizes this provider result rather than exposing the upstream code/string.

### Git worktrees

After committing the tracked `.beads` files and creating a Git worktree, `br` resolved that worktree's own `.beads` directory and lazily built a separate ignored SQLite database from its checked-out JSONL. It did not automatically redirect to the control checkout.

This confirms the initial architecture assumption: one configured control checkout owns every work-graph mutation. Worker worktrees never call `br`; the work adapter receives the control checkout explicitly. A worker checkout's local `br` database is neither current coordination state nor an authority.

### `bv` compatibility and advice binding

`bv v0.18.0` read the `br v0.1.45` workspace directly. `--robot-next` returned a recommendation, reasons, `version`, `generated_at`, phase completeness, and a 16-hex `data_hash`; `--robot-graph` returned the expected two-node dependency edge and the same data hash.

The `bv` data hash is not the same representation as `br`'s JSONL content hash. The adapter binds advice with a stable-read bracket:

1. read `br` JSONL content hash;
2. invoke `bv` with an explicit database/workspace and deadline;
3. read the `br` hash again;
4. accept advice only if the before/after `br` hashes match, the `bv` schema/version is valid, and the response carries its own data hash.

Provider-emitted `claim_command` and `show_command` values used lowercase IDs and raw `br` commands. They are untrusted convenience strings and must be discarded, never shown to roles or executed.
