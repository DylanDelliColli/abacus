## Observations

### Prefix mapping

`br init --prefix ABACUS` succeeds but normalizes generated IDs to lowercase (`abacus-...`). Setting `issue_prefix=ABACUS` later preserves the displayed config value while the computed prefix and newly generated IDs remain lowercase. Lookups are case-insensitive: `br show ABACUS-aon --json` resolves the stored `abacus-aon` record.

ABACUS therefore needs an explicit lossless seam mapping:

```text
ABACUS external ID: ABACUS-<lowercase suffix>
br provider ID:     abacus-<lowercase suffix>
```

Lowercase provider IDs and provider-generated command strings never cross the work facade. Fresh ABACUS initialization rejects conflicting/mixed graphs rather than guessing a mapping. This preserves the binding `ABACUS-` product namespace without forking `br` solely for case presentation.

### Label storage constraints

Pinned `br` does not accept the proposed scope-label spelling `key=value`. Adding `area=a` returned exit code `4`, structured code `VALIDATION_FAILED`, and the provider rule “only alphanumeric, hyphen, underscore, colon allowed.” The provider accepted `area:a`. A 50-character label succeeded; a 51-character label returned the same structured validation code with reason `exceeds 50 characters`.

The provider also does not enforce key cardinality: sequential additions of `area:a` and `area:b` both succeeded and `br label list` returned both values. Any scope design backed by work labels must therefore choose a provider-compatible encoding and have `abacus-work` validate the declared-key representation, including a single-value rule if the scope algebra treats attributes as a map. Provider acceptance cannot be that authorization invariant.

### Machine operations and graph semantics

The spike exercised JSON output for initialize, create, show, ready, update, dependency-add, close, list, info, and sync-status. Dependency direction matched the required contract: `br dep add child blocker` removed the child from `ready`; closing the blocker made the child ready.

`br close ... --reason accepted_handoff --json` persisted and returned the curated close reason. The adapter can therefore render the bounded ABACUS reason code directly and must reject arbitrary/unbounded message content before invoking the provider.

Mutations auto-flushed `issues.jsonl`. `br sync --status --json` returned `dirty_count: 0` and a 64-hex `jsonl_content_hash`, suitable as the provider revision observed before and after composed reads.

### Concurrency

Two simultaneous atomic claims against one open bead produced exactly one success. The loser returned exit code `4` with structured code `VALIDATION_FAILED`, a field/reason context, and `retryable: true`; the database remained readable. ABACUS still serializes decision-gated mutations at its use-case boundary and normalizes this provider result rather than exposing the upstream code/string.

An exclusive SQLite writer held outside `br` produced a different shape. A contending `br create` invoked with `--lock-timeout 100` waited about 15.9 seconds, then returned exit code `2`, structured code `DATABASE_ERROR`, message `database is busy`, and `retryable: false`; neither baseline issue changed and no contender was created. The provider busy timeout is therefore not a sufficient whole-operation deadline.

Historical conclusion (superseded by ADR-0006): this originally reinforced one
exclusive `abacus-work` writer with workers reporting through Scribe. The
observed provider facts still hold—claim has one winner and provider timeout is
not a whole-operation deadline—but v1 now permits trusted-local direct writers
against one explicitly shared `BEADS_DIR`.

### Destructive sync and database recovery

All cases used independent disposable clones of a two-issue baseline.

- Importing JSONL containing Git conflict markers returned exit code `7` and structured `CONFIG_ERROR` before mutation. `--force` returned the same failure. The database retained both original issues.
- Appending an incomplete third JSON object returned exit code `7` and structured `CONFIG_ERROR` with the invalid line/column. `--force` did not bypass validation. The database retained both original issues.
- After a WAL checkpoint, truncating the active database to 17 bytes and temporarily withholding JSONL produced exit code `2`, structured non-retryable `DATABASE_ERROR`, and a specific malformed-image diagnostic.
- With intact JSONL, the same 17-byte corruption was recovered automatically during an ordinary read even with automatic import/flush disabled: `br` quarantined the damaged database, rebuilt two records, and returned success. `doctor` then returned top-level `ok: true` while reporting `db.recovery_artifacts` as a warning. Explicit `sync --import-only --rebuild` also recovered successfully.

Recovery-artifact presence alone does not prove unexpected corruption: an intentional `--rebuild` also preserves the replaced database family. A work diagnostic must interpret individual doctor checks and operation context rather than trusting only top-level `ok` or treating every preserved backup as corruption.

### Interrupted flush and rebuild

A 1,000-record, 33 MB graph made the atomic-write windows observable.

- A flush was sent `SIGKILL` only after `issues.jsonl.3.tmp` appeared. The canonical JSONL retained its exact pre-run SHA-256, remained valid with 1,000 records, and the database retained one dirty item. The partial temp file was 33,038 bytes with no complete record. A normal retry exported all 1,000 issues, cleared the dirty item, and installed a new canonical hash; the partial numbered temp file remained.
- A rebuild was sent `SIGKILL` only after a new recovery artifact appeared. The canonical JSONL retained its exact hash and all 1,000 valid records, while the active database family was absent and the original family was preserved under `.br_recovery/`. Re-running the same explicit rebuild created all 1,000 records, passed SQLite integrity checking, and left the JSONL hash unchanged.
- A separate later interruption left a valid but empty database beside the intact 20,000-record JSONL. `doctor` still reported top-level `ok: true`, with warnings for recovery artifacts and a `counts.db_vs_jsonl` mismatch. Callers must inspect the named checks and reconcile before allowing work reads.

The adapter-visible fixtures are checked in under [`abacus-work/fixtures/br-v0.1.45/`](../../abacus-work/fixtures/br-v0.1.45/). Interrupted operations normalize to an ambiguous/interrupted mutation requiring inspection; numbered temp files are never canonical input. A flush retry is safe after status/hash inspection. A missing or count-mismatched database blocks work reads until explicit JSONL validation and rebuild complete.

### Git worktrees

After committing the tracked `.beads` files and creating a Git worktree, `br` resolved that worktree's own `.beads` directory and lazily built a separate ignored SQLite database from its checked-out JSONL. It did not automatically redirect to the control checkout.

This observation now supports ADR-0006's explicit-store rule rather than the
initial exclusive-writer conclusion. A worker checkout's locally discovered
database is not coordination state. Every worker instead receives the control
checkout's absolute `BEADS_DIR` (and, for Codex, that exact writable root), so
all direct stock-`br` calls address one store without JSONL merge arbitration.

### `bv` compatibility and advice binding

`bv v0.18.0` read the `br v0.1.45` workspace directly. `--robot-next` returned a recommendation, reasons, `version`, `generated_at`, phase completeness, and a 16-hex `data_hash`; `--robot-graph` returned the expected two-node dependency edge and the same data hash.

The `bv` data hash is not the same representation as `br`'s JSONL content hash. The adapter binds advice with a stable-read bracket:

1. read `br` JSONL content hash;
2. invoke `bv` with an explicit database/workspace and deadline;
3. read the `br` hash again;
4. accept advice only if the before/after `br` hashes match, the `bv` schema/version is valid, and the response carries its own data hash.

Provider-emitted `claim_command` and `show_command` values used lowercase IDs and raw `br` commands. They are untrusted convenience strings and must be discarded, never shown to roles or executed.
